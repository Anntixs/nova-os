# SMP bring-up status

## IMPLEMENTED / EXPERIMENTAL

NovaBoot protocol v2 reserves one UEFI LoaderData page below 1 MiB when available. The BSP copies a position-independent trampoline to that page, patches physical GDTR, jumps, CR3, AP stack, logical index and Rust entry, then sends INIT/deassert/SIPI (with one SIPI retry) through xAPIC ICR. The AP runs 16-bit real-mode code, enables protected mode, PAE and long mode, loads the BSP's identity-mapped kernel CR3, switches to its dedicated stack, and enters Rust. The AP loads its own GDT, TSS, IST stacks and IDT, enables NX and Local APIC, writes its GS-based CPU-local record, acknowledges, then idles with HLT. Startup is sequential and bounded by timer deadlines. QEMU `-smp 4` acknowledged APIC IDs 1–3; `-smp 8` acknowledged IDs 1–7.

If an IPI fails or an AP misses its acknowledgement deadline, BSP stops starting further APs. The trampoline page is shared; reusing its patched stack or logical ID while a late AP may still be starting could corrupt another CPU's execution state. A late AP remains outside the scheduler.

**Only the BSP is scheduler-online.** AP acknowledgement proves execution of Nova AP code, not multi-CPU task scheduling. `/proc/cpuinfo` separates discovered CPUs, APs that entered Nova, and CPUs admitted to the scheduler. The AP limit is eight preallocated slots. If NovaBoot cannot reserve a suitable low page, the kernel continues on the BSP.

The optional `NOVA_SMPTEST=1` build mode runs 256 physical-frame and heap allocation/verification cycles on each AP. QEMU with four CPUs completed this cross-CPU allocator probe and the normal userspace regression. The scheduler has a pinned host context, host CR3 and current-thread slot for each of eight CPU records; only the BSP slot is used to run threads. A yielding, blocking or exiting thread now stays Running and owned by its CPU until that CPU has switched to its host stack. The host then publishes the new state under the scheduler lock, so an AP cannot claim its live kernel stack. The process manager now keeps stable process entries and one active PID slot per logical CPU; its process-table lock masks local IRQs. The four-vCPU QEMU userspace regression passed with this table, but AP task scheduling has not been enabled. IPC blocking/wakeup across active scheduler CPUs remains untested.

The syscall entry no longer uses global stack/RSP scratch variables: it obtains both from a trusted CPU-local GS record. First Ring 3 entry, syscall, IRQ and fatal exception paths pair their GS transitions. A userspace regression program loads a null GS selector, exercises syscalls and waits for a timer IRQ, then confirms that the kernel remains alive. The scheduler and process manager have CPU-local running slots, but their cross-CPU behavior and the shared userspace services still need verification before AP user threads can run.

Each AP now programs its own SYSCALL MSRs during entry. The scheduler's RSP0 setter selects the TSS owned by the current CPU, so a future AP thread dispatch cannot overwrite the BSP's ring-transition stack. These are prerequisites only; APs still do not run ordinary kernel or user threads.

The QEMU startup and userspace regression matrix passed with `-smp 1`, `2`, `4`, and `8`. A separate `-smp 4 -m 4G` run with `NOVA_SMPTEST=1` passed. These tests establish AP entry and allocator concurrency only; they do not establish SMP scheduling, process-table concurrency, VFS concurrency, or hardware support outside QEMU.

Vector 240 now has an IPI handler that reloads the receiving CPU's CR3, then publishes an acknowledgement. In `NOVA_SMPTEST=1`, the BSP sent that IPI to all three APs in QEMU `-smp 4` and observed all three acknowledgements. This validates the interrupt route and local flush operation. It does not yet track which address space each CPU runs or serialize concurrent shootdown requests, so user mapping changes still cannot rely on it for AP scheduling.

## PLANNED before Stage B

Cross-CPU testing of the context-switch handoff and process table, a complete address-space-aware TLB shootdown protocol, interrupt-safe blocking synchronization, reschedule IPIs and concurrent stress tests. Mapping and unmapping a user page currently switch CR3 and invalidate translations only on the calling CPU. A process running on another CPU could retain a stale TLB entry after `munmap`; consequently AP user-thread scheduling must remain disabled until remote invalidation and address-space lifetime are solved. The block registry, FAT32 transaction, TTY, keyboard queues, formatted log and terminal output now have cross-CPU exclusion, but have not been stress-tested with AP user threads. Existing locks that only clear local IF are not SMP-safe. No NVMe/AHCI/USB work should begin until this stage is stable.
